# Keypad UI Redesign: Spec and Acceptance Tests

> **For agentic workers:** this replaces the form UI built in Task 8 of `2026-10-30-fullstack-calculator.md`. Follow TDD: write the reducer tests from the table below first, then the component tests, then implement. Commit as `feat(frontend): keypad calculator UI`. Don't change the backend or the API client contract. QA verifies every row in the acceptance table in the browser.

**Why:** the assignment asks for an "intuitive UI for entering input and displaying results". Two text boxes and a row of radio buttons is a form, not a calculator. People expect a display and a keypad with digits 0–9, operators, `=`, `AC` and backspace, plus keyboard support on desktop.

## Architecture

The existing layers stay: `src/api/calculator.ts` (unchanged) and `useCalculation` (reused for the request, abort and stale-response logic). What's new:

| File | Responsibility |
|---|---|
| `src/features/calculator/keypadReducer.ts` | **Pure** state machine: `(state, action) => state`. No I/O. When a calculation is needed it records a `pending` request `{ operation, operands, label }` in state. |
| `src/features/calculator/keypadReducer.test.ts` | One test per row of the acceptance table below (behaviour only, no DOM) |
| `src/features/calculator/keys.ts` | The key list (id, label, aria-label, kind: digit / op / fn / equals, grid span) and the keyboard map. The keypad renders from this list. |
| `src/features/calculator/Display.tsx` | Expression line, value (an `<output aria-live="polite">`), error line (`role="alert"`) |
| `src/features/calculator/Keypad.tsx` | The 4-column button grid, built from `keys.ts` |
| `src/features/calculator/Calculator.tsx` | Wires the reducer to `useCalculation`. A `pending` request triggers `run()`, and the result or error is dispatched back as `resolved` / `failed`. Also handles the document-level `keydown` listener. |
| `src/features/calculator/format.ts` | Keep. Fix: large integers are also capped at 12 significant digits (QA round 1, minor finding). |

Delete `NumberField.tsx` and the radio-button markup. Also delete `validation.ts` and its tests, because keypad input can't be malformed:

- A number can have at most one decimal point.
- An entry can have at most 15 digits.
- There are no leading zeros.

The backend still validates everything. Say this in the README design decisions.

## State and actions (contract)

```ts
type BinaryOp = 'add' | 'subtract' | 'multiply' | 'divide' | 'power' | 'percentage';

interface KeypadState {
  entry: string;              // what the value line shows, e.g. "0", "-12.5"
  left: number | null;        // first operand once an operator is chosen
  operator: BinaryOp | null;  // chosen operator, highlighted (aria-pressed) until the next digit
  expression: string;         // expression line, e.g. "12 ÷", "12 ÷ 4 =", "√9 ="
  overwrite: boolean;         // the next digit replaces entry (after an operator, result or error)
  error: string | null;       // user-facing error copy
  pending: { operation: Operation; operands: number[]; label: string; then: BinaryOp | null } | null;
}

type Action =
  | { type: 'digit'; digit: string } | { type: 'decimal' } | { type: 'backspace' }
  | { type: 'toggleSign' } | { type: 'clear' } | { type: 'operator'; op: BinaryOp }
  | { type: 'sqrt' } | { type: 'equals' }
  | { type: 'resolved'; result: number } | { type: 'failed'; message: string };
```

While `pending` is set, every action except `clear`, `resolved` and `failed` is ignored. `clear` also aborts the in-flight request. `then` carries a chained operator: after `2 + 3 ×` resolves, the state becomes `left = 5, operator = multiply`.

### Error copy (map `ApiError.code` in the component, not the reducer)

| Code | Text |
|---|---|
| `division_by_zero` | You can't divide by zero. |
| `negative_sqrt` | Square root needs a number of 0 or more. |
| `result_out_of_range` | That result is too large to show. |
| `network_error` | Couldn't reach the calculator service. Try again. |
| any other | the server `message`, or "Something went wrong. Try again." |

### Keyboard (document-level `keydown`; ignore events with Ctrl or Meta held)

| Key | Action |
|---|---|
| `0`–`9` | digit |
| `.` and `,` | decimal |
| `+` `-` `*` (and `x`) `/` `^` `%` | operator |
| `Enter`, `=` | equals, but **only when focus is not on a keypad button**. When a `<button>` has focus, Enter and Space must activate that button natively (WAI-ARIA button pattern). Corrected in QA round 2. |
| `Backspace` | backspace |
| `Escape`, `Delete` | clear |
| `r` | sqrt |

### Accessibility and layout

- Every key is a `<button type="button">` with an `aria-label` for symbol keys ("Divide", "Square root", "Backspace", "All clear", "Toggle sign", "Decimal point", "Equals", "Percent of", "Power").
- The current operator key has `aria-pressed="true"` and a visible state.
- The value is an `<output aria-live="polite">`, and errors are `role="alert"`.
- The keypad is a 4-column CSS grid. Keys are at least 56px tall. The card is at most 360px wide and fills the width on phones, with no horizontal scroll at 375px.
- Long values shrink their font, and never wrap mid-number (QA round 1, minor finding).
- Visual hierarchy: digits on the plainest surface, functions on a muted surface, operators on an accent tint, and `=` as the only solid accent key.
- Tests use `getByRole('button', { name: … })`, `user.click` and `user.keyboard`, never class names.
